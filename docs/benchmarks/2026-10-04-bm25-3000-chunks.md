# BM25 cost on a long chat (synthetic, 300 and 3000 chunks)

Measured for v4 (keyword search and fusion). Feeds v6: the "time" column of the evaluation should be read against these numbers.

## Machine and setup

| | |
|---|---|
| Date | 2026-10-04 |
| CPU | Intel Core i9-10885H @ 2.40 GHz (8 cores / 16 threads) |
| RAM | 31.7 GB |
| OS | Windows 11 Pro (10.0.26200) |
| Runtime | Node v24.14.1 (V8), vitest 5.0.0 |
| Run with | `npm run bench` (`bench/bm25.bench.ts`, own config `bench/vitest.config.ts`) |
| Method | 3 warm-up runs, then 20 timed runs per case, `performance.now()` |

## What was measured

Only the pure ranking code in `src/rag/` (`tokenize.ts`, `bm25.ts`, `fusion.ts`). **IndexedDB read time (`getAllChunks`, `getAllEmbeddings`) is not included**, and in real use it is the larger cost, because the embedding vectors come with it.

The text is **synthetic**, generated from a seeded random word list (fixed seed, so runs are comparable), never real chat content:

- 300 chunks = 392,656 characters; 3000 chunks = 3,908,735 characters.
- Each chunk is 100–179 words from a 5000-word vocabulary skewed towards common words.
- 10% of chunks are "code": one token per line, 30% of them `snake_case_name`, `camelCaseValue` or `UPPER_CASE` identifiers.
- `pool_pre_ping=True` is planted in a handful of chunks so identifier queries have something to find.
- Queries: one identifier (4 tokens after splitting), a 3-word query, and a 200-word "paragraph" query (175 unique terms).

## Results

All times in milliseconds (mean of 20 runs; p95 and max are in the raw output of `npm run bench`).

| case | 300 chunks | 3000 chunks |
|---|---:|---:|
| **Cold** (first search after page load; nothing cached) | | |
| build index (tokenise + term statistics) | 19.1 | 187.1 |
| full search, identifier query (build + score) | 18.2 | 193.7 |
| full search, 200-word paragraph query (build + score) | 20.2 | 234.0 |
| **Warm** (term counts cached by `textHash`; the normal case) | | |
| build index, nothing changed | 2.4 | 33.8 |
| build index, 1 chunk edited | 2.7 | 36.4 |
| full search, identifier query | 2.7 | 32.0 |
| full search, 200-word paragraph query | 4.3 | 49.3 |
| **Scoring alone** (index already built) | | |
| 1 identifier query | 0.09 | 0.7 |
| 3-word query | 0.15 | 3.3 (median 1.7; one 29 ms GC outlier) |
| 200-word paragraph query | 1.8 | 21.2 |
| **Fusion** | | |
| reciprocal rank fusion of two 50-entry lists | 0.03 | 0.02 |

## What this says

- **No inverted index is needed.** Scoring is linear in chunks × query terms and stays small. Fusion is negligible.
- **Tokenising was the cost, and my first estimate was wrong.** Before any optimisation the cold build for 3000 chunks was about **580 ms** (and about 58 ms for 300), against the 100–300 ms I had estimated in the plan. Two changes brought it down:
  1. A fast path in `tokenize()` for tokens with no split point (plain words, which is most of them) skips the regex-replace/split work: 580 → 187 ms, about 3×.
  2. A per-chunk term-count cache keyed by `Chunk.textHash` (`Bm25TermCache` in `bm25.ts`, held in memory by `hybridSearch`): a warm search no longer tokenises anything. The decision rule written into the v4 plan was "add the cache if the 3000-chunk build is above ~50 ms"; it was (187 ms even after the fast path), so the cache was built.
- **What is left on the warm path** (about 32 ms at 3000 chunks) is rebuilding the document-frequency table by walking every chunk's term list. It could be made incremental, but it is under the ~50 ms line, so it was not built.
- **The cold cost is paid once per page load per conversation** (the first search after reloading the tab or the extension). An edited chunk costs a single re-tokenise (row "1 chunk edited").
- Even the worst warm case (3000 chunks, a pasted 200-word highlight, ~49 ms) is small next to a Gemini request, and next to reading all chunks and vectors out of IndexedDB.

## Caveats

- Node's V8, not Chrome's content-script environment. Same engine family, but a busy claude.ai page competes for the main thread, so treat these as a floor, not a promise.
- Synthetic text. Real chats have different word-length and identifier distributions; the shape of the result (linear, tokenising-dominated) should hold, the absolute numbers will move.
- A laptop, with whatever power state it was in. Run-to-run variation on the same code: about 1% at 3000 chunks, but up to about 30% at 300 chunks (the cold 300-chunk build measured 28 ms in one run and 19 ms in another), so treat the small-chat numbers as order-of-magnitude.
- 3000 chunks (~3.9 MB of text) is deliberately extreme: it is roughly a 700-message chat. The user's real chats are mostly far smaller; at 300 chunks every path above is under 25 ms cold and under 5 ms warm.
